# Builds and compatibility

The binary is always named lanescape-browser. The package major is unstable while `Cargo.toml` sets `[package.metadata.lanescape-browser] unstable = true`. The flag is set when a breaking change needs a new major, in the PR that bumps the package to `N+1.0.0`; a maintainer clears it in an ordinary PR once Lanescape, the only consumer today, has integrated that major, which freezes its contract. Additions, removals and incompatible changes are allowed within an unstable major without a major bump. Update its schema, specifications and native contract fixtures together. Stable majors preserve their existing wire and behavioural contracts; breaking changes require a new major protocol and storage prefix, such as v2. Each binary speaks one major; no binary serves two majors.

Only pushes to main and to `support/vN` branches allocate date-based UTC build numbers. Build numbers share one tag namespace across branches. Reserve YYYYMMDD.N at workflow start with a build tag pointing to the exact commit; failed builds may leave gaps. All matrix jobs use the same number. PRs to main or a support branch receive no build number, and their packages are kept only to hand them to a test machine, for a day. Every PR and push builds each target once, optimised, against the pinned libchromium, and runs every suite on its package on a machine like the target's (ci/README.md). Each build restores and saves its target's cache, `build-<target>` in `.github/runners.json`, in the runner service's scopes: main and support branches never read a cache that PR code wrote. Packages are compressed with pigz into standard gzip tarballs. Caches contain no credentials. Use the latest stable GitHub Actions releases, with Node 24 or newer for JavaScript actions.

Packages contain the native executable, the Rust host library, libchromium's shared library and runtime files beside them, and license notices: Lanescape browser's license, libchromium's notices, which say where Chromium's corresponding source is, libvpx's, and the Rust crates' (third_party/README.md). `scripts/build.py package` makes one from a build. Linux executables and libraries ship stripped of debug information and symbol tables; macOS ones ship without local symbols and signed ad hoc. Publish three native targets: linux-amd64, linux-arm64 and macos-arm64. A manifest records commit, major, build, each package's size and SHA-256 digest, and the libchromium version the build was made with, whose GitHub release publishes Chromium's corresponding source (third_party/README.md). Package objects are immutable and the complete manifest is uploaded last.

Build tags are `v<major>.YYYYMMDD.N`, such as `v1.20261107.1`: valid semver, with the date as minor and the daily counter as patch. The counter is shared by all branches and majors, so `YYYYMMDD.N` alone identifies a build: reservation counts the day's build tags of every major and keeps a number only if, listed once its own tag exists, no other commit has a tag for it; otherwise it takes the next number, even on a rerun. A number tagged on more than one commit belongs to the commit published under it. The Version handshake, manifests and bucket keys use the bare build number. `lanescape-browser --version` prints the major and build, such as `lanescape-browser 1.20261107.1`, or `lanescape-browser 1.development` without a build number. A repository ruleset protects `v*` tags from being moved or deleted. There is no moving major tag and no workflow runs on tag pushes.

`vN/latest` in the bucket is a major's only pointer to its current build. It contains the build number and a newline and uses no-store caching. Promotion only moves it forward, without exceptions, and every promotion goes through `scripts/release.py promote`, which refuses unless the build's manifest `vN/<build>/manifest.json` exists (it is written last and immutably) and names the build's commit, all three packages verify against it, it names the libchromium release that `engine/libchromium.json` pins at the commit, the commit is on main or `support/vN` with package major N in its `Cargo.toml`, and, if `vN/latest` exists, the commit strictly descends from the commit of the build it names. Promoting the current build changes nothing. `vN/latest` and its ETag are read in one request, and the write is conditioned on that ETag (`If-Match`), or on its absence (`If-None-Match: *`), which R2 evaluates atomically; after a failed precondition, promotion reads it again and repeats the check, a bounded number of times. This compare-and-swap keeps concurrent promotions forward-only in every order; serializing promotions of a major only saves retries. Promotion does not rebuild packages.

CD promotes each published build of an unstable major (`promote --if-unstable`, which does nothing when the build's `Cargo.toml` does not flag its major unstable). A stable major's build is promoted only when a maintainer dispatches the Promote build workflow from main or `support/vN` with its build number. That job runs in the `promote` environment, whose required reviewers approve it.

Rollback is a revert PR: its build gets a new number and is promoted forward like any other. A consumer that must stay on one build in an emergency pins that build itself; `vN/latest` never moves backwards.

Preserve corresponding engine source availability: libchromium keeps a version's release for as long as any build that uses it is downloadable. Pointing to the private application repository or shipping SDK headers does not satisfy that obligation.

`Cargo.toml` defines the package major. It is the only version source: the storage prefix, the protocol major reported by Version, and `--version` all derive from it. Proto paths/packages, capability tokens and test names carry no major. A build is promoted only under the package major of its commit. Native tests, package checksums and corresponding-source verification remain required whether or not the major is unstable.

## Publishing

Builds are published to the private Cloudflare R2 bucket `lanescape-browser`, in account `6d39a82297745b856f8c09e7e0b91b3a`, which `.github/release.json` names; neither is secret. Its keys are `vN/<build>/lanescape-browser-<target>.tar.gz`, `vN/<build>/manifest.json` and `vN/latest`. Packages and manifests are written once, with `If-None-Match: *`, `Cache-Control: public, max-age=31536000, immutable` and their SHA-256 as `x-amz-meta-sha256`; a retry that finds the same object accepts it, and a different one is a conflict. `vN/latest` is `Cache-Control: no-store`. `scripts/storage.py` speaks R2's S3 API with the standard library alone, signing with AWS Signature Version 4, region `auto`, and the payload's SHA-256, which R2 checks; `scripts/github.py` calls GitHub's API for build tags, since the runner service's machines have no `gh`.

Everyone downloads through `https://downloads.lanescape.dev/lanescape/browser/<key>`, such as `https://downloads.lanescape.dev/lanescape/browser/v1/latest`, which redirects to a short-lived presigned URL of the object (lanescape/downloads, which holds its own read-only token). Those addresses don't change if the bucket does, so apps may embed them.

Each push's packages are the exact bytes its suites tested: CD keeps them as artifacts for a week (a pull request's, a day), and the publish job uploads those. A publish that stopped partway is retried by rerunning the failed job in that week, and accepts what it finds already uploaded. A rebuild of the same commit gives different bytes, which publishing refuses as a conflict, so once the artifacts are gone the change is published from a new commit, with a new number. Before it uploads anything, and again when it promotes, CD checks that the pinned libchromium release publishes its corresponding source: its manifest lists source archives, and the release has each at its size.

CD's `publish` job, once every target's suites pass, runs `scripts/publish.py`, then `release.py promote --if-unstable`. It and the Promote build workflow sign their requests with an R2 API token that may read and write this bucket alone, as the GitHub secrets `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` of the `publish` and `promote` environments. Only `main` and `support/v*` may use either environment, so no pull request's code can reach the token, and the `promote` environment needs a maintainer's approval. The reservation job alone may write the repository's contents, to create the build tag.

## Support branches and breaking changes

Main builds the newest major. When a breaking change is needed in stable major N:

1. Create `support/vN` from main's last successfully published numbered vN commit (its manifest is complete). Its creation push does not rebuild; that commit keeps its main build number and can be promoted as vN. Later vN fixes are PRs targeting `support/vN`, and each push there allocates a new build number. List it in main's `.github/runners.json` under `"branches"`, as `{"support/vN": "vN"}`, so that its pushes save caches of their own (ci/README.md).
2. The breaking PR to main bumps `Cargo.toml` to `N+1.0.0` and sets `unstable = true`, together with its schema, specifications and contract tests. Once `support/vN` exists, main refuses to build while its package major is still N, so main cannot publish into the support branch's prefix.
3. After that PR merges, main's builds publish under `vN+1/`, and CD promotes them while vN+1 is unstable; the first creates `vN+1/latest`.

A `support/vN` branch builds and publishes only when its package major is N. Promotion as vN is refused for a commit whose package major differs, including main commits after the bump. CI runs on PRs to main and to `support/v*`. Protect `support/v*` branches like main in the repository settings.

Manifests do not label stability: automatic promotion reads the flag from `Cargo.toml` at the build's commit.

v1 is unstable until Lanescape has integrated it.
