# RFB display

RFB 3.8 is the sole display protocol. It runs on owner-private Unix sockets, intended for forwarding inside authenticated SSH. RFB security type None is appropriate only inside that private transport. A tab accepts at most eight viewers; each is initially view-only. The supervisor selects its controller over the protobuf channel.

Support Raw (0), ZRLE (16), DesktopSize (-223) and FrameSequence (0x4C534653, ASCII "LSFS"). Initial pixels are little-endian 32-bit true colour with 24-bit RGB depth, shifts 16/8/0. SetPixelFormat accepts valid true-colour 8-, 16- and 32-bit formats, either byte order, with nonoverlapping contiguous component masks. Indexed colour is unsupported. Each SetEncodings replaces the viewer's choice: every update encoded after the engine reads it uses ZRLE when that SetEncodings lists ZRLE, and Raw otherwise. Before any SetEncodings, updates use Raw. ClientCutText is bounded and discarded: clipboard exchange and input-method composition use the control channel's `clipboard` and `native-ime` capabilities (0002-control.md), never RFB.

Each viewer has a persistent zlib stream. ZRLE uses 64×64 tiles, raw or solid when a tile is all one colour, with compact pixels as defined by RFB. Full requests receive the requested image region. Chromium says which part of each captured frame changed, which is tightened against the frame it replaces, so a frame copies only what changed and an incremental update sends the bounding rectangle of what changed since that viewer's last update. A viewer that has fallen more than 64 frames behind receives its whole request. Unchanged regions produce no update. A request starting outside the framebuffer, as one sent before it shrank, is answered with an update carrying no pixels. A partial request never acknowledges changes outside its region. Encoded updates are ordered; never discard a dependent rectangle after encoding it. Newly connected viewers receive a full image.

Each publication of a tab's framebuffer, popups composed in, has a sequence number: it starts at 1, increases by one each time and is never reused while the tab lives. It identifies a publication, not distinct pixels: identical pixels can be published again under a new number. A viewer that lists FrameSequence in its latest SetEncodings receives, as the first rectangle of every update, a pseudo-rectangle with x, y, width and height 0, encoding FrameSequence and then 8 bytes holding the big-endian sequence of the framebuffer the update was encoded from. The update's rectangle count includes it. A partial request's update carries it too. Other viewers receive unchanged updates. A viewer opts in through SetEncodings alone, independently of Initialize. A viewer pairs this with DisplayFence (0002-control.md): the first complete frame with a sequence of at least S holds what the fence promised. A viewer holding an older frame sends a full request, which is always answered.

DesktopSize precedes pixels when dimensions change. Viewers that do not advertise DesktopSize must reconnect after resize. Capture is of the tab's whole window, so `<select>` popups, which are separate widgets, are part of the image. A viewer's first frame is the page's first paint.

RFB encoding and socket waits run outside Chromium's UI thread. The latest frame is reference-counted; a viewer reading it keeps it, and the next frame goes elsewhere, rather than any encoded frame queue. A viewer sleeps until a frame arrives. While a tab has no viewer and no fence is waiting, it is captured once a second rather than at the 30 frames a second it otherwise is at most. Writes time out after five seconds. The display loop continues reading input while an incremental request waits for a paint. Keyboard messages support conventional navigation/modifier/function keys, the keypad, Latin-1 and Unicode keysyms; left and right modifiers are held independently. Pointer messages support buttons and vertical and horizontal wheel input (buttons 4–7). Printable ASCII keysyms use their US-layout key, so a shifted digit is that digit's key. RFB carries no click count: a press of the same button within 500 ms and 4 pixels of the last counts up, giving double and triple clicks; a fourth press starts over at one.

GPU acceleration applies to browser rendering and compositing, and to a capture's colour conversion. RFB compression and VP8 encoding run on the CPU in both rendering modes; the display makes no GPU-handle or zero-copy promise. It works without shared memory, DMA-BUF negotiation or a display server. Linux hardware rendering uses headless Ozone with ANGLE/Vulkan; CPU operation requires neither X11 nor Wayland. macOS hardware rendering uses ANGLE/Metal, and a tab shows nothing on the machine's displays in either mode.
