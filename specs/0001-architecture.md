# Architecture and isolation

Lanescape browser is a thin embedder of Chromium's Content API. It never compiles Chromium: `engine/` holds its C++ delegates, which compile against libchromium (`lanescape/libchromium`), upstream Chromium built as one shared library with its headers, flags and toolchain, at the version `engine/libchromium.json` pins, and link that library. It uses only what libchromium exports, with no patches to Chromium of its own and no internal headers. Its renderer agent's interfaces (`engine/lanescape_browser.mojom`) are generated with libchromium's mojom tooling. The recorder's VP8 encoder is libvpx, at the release `engine/libvpx.json` pins, built for each target with libchromium's toolchain and linked statically, its symbols hidden from Chromium's own copy. The executable loads the Rust host, `liblanescape_browser_host.so` (`liblanescape_browser_host.dylib` on macOS), which speaks the control protocol and RFB; the two talk through the small C interface in `engine/lanescape_browser.h`. A change to the host alone compiles only Rust, and a change to the embedder compiles only `engine/` and links.

One Lanescape browser host serves one environment. Chromium retains its normal multiprocess renderer and sandbox architecture. Each profile has one persistent browser context. Tabs within that profile share cookies, cache and site storage; other profiles do not. Profile names are opaque; what they mean belongs to the supervisor.

Every independently created private tab has a separate in-memory browser context. Popups inherit the opener's context. A private context goes when its final tab closes. Private tabs and their navigation state are never restored after a restart. Private browsing prevents deliberate application persistence, not operating-system swap or access by privileged processes.

Each browsing context has its own clipboard, holding data only for the frame running its current operation, so that one process can serve any number of contexts. Nothing reaches the operating system's clipboard: frames get our own `ClipboardHost`, and `ui::Clipboard`, which everything else in Chromium goes through, is an inert one that keeps nothing.

A frame's renderer runs a small agent (`engine/renderer.cc`, `engine/lanescape_browser.mojom`) over interfaces associated with the channel, so they stay in order with each other and with the frame's own messages to the browser. IME actions and clipboard commands run there, where checking that focus is still as reported and acting on it are one step. Input reaches a renderer by another path, so the tab keeps a viewer's input and these commands strictly in order: a command waits for earlier key and button events to be acknowledged, and later input waits for it to start.

The browser uses the server's network directly. There is no HTTP proxy or host mapping. The Lanescape server supervises this process and forwards RFB over SSH. Its MCP tools, and every concept about agents, live there; this engine offers tab-bound DevTools sessions.

On Linux each tab has its own window tree host with no platform window behind it, really shown, and a video capturer on its root, which includes `<select>` popups. On macOS, where Chromium has no Aura, each tab's Cocoa views have no window, as in Chromium's own headless mode, and are really shown; the capturer follows the page's view, and each popup, a widget with a window and compositor of its own placed out of sight, is captured too and composed into the tab's captures. Input reaches the widget under the pointer, or with focus, through Chromium's hit test, and Command's editing shortcuts run as the system's Edit menu would run them. RFB encoding and network waits occur outside Chromium's UI thread. Rendering prefers the GPU and falls back to the CPU: `--rendering=auto`, the default, uses Vulkan through ANGLE on Linux and Metal through ANGLE on macOS where it can, Status reports what Chromium is actually compositing with, and software operation works without a GPU or a display server. Chromium sandbox failure must not silently enable `--no-sandbox`; the host stops if the renderer sandbox isn't active. On macOS that is Seatbelt: the host checks the renderer process itself is sandboxed and denied the data directory, and won't start inside a sandbox of its own, which would leave its renderers unable to enter theirs.

Native contract tests and corresponding-source publication must succeed before a build manifest is published. Unstable majors are specified in 0004-releases.md.

Optional file-picker, download and native-menu interactions keep authority in this server process. The supervisor owns authentication, server-path authorization, file-byte transport and native client UI. No server path is interpreted as a client-local path; no client-local browser is involved. Completed downloads and staged uploads are supervisor-owned artifacts requiring private-context cleanup; unfinished downloads remain engine-owned until termination. File pickers and downloads aren't implemented yet (0002-control.md).

DevTools sessions attach to one tab's agent host, so each is bound structurally to one tab and its browser context. The browser-wide `--remote-debugging-pipe` reaches every profile and private context, and is never used or exposed. A session reaches what the tab's pages can reach and never data Chromium hides from page script. Its clients are untrusted: it names no server file, and tabs navigate only to web pages (0002-control.md).

User preferences (colour scheme, timezone and languages) come from the supervisor and apply to the whole host. The user is usually on another machine, so the host's own settings mean nothing to them; supervisors set all three. They aren't implemented yet (0002-control.md).
