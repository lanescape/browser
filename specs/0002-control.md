# Control

The authoritative definitions are `proto/lanescape/browser/control.proto` (package `lanescape.browser`). Requests arrive on stdin; Output messages leave stdout, which nothing else in the process writes to: libraries and helper processes get stderr in its place. Each protobuf has a four-byte little-endian length prefix, nonzero and at most 65536 bytes. EOF shuts down the host. The engine never shows modal error dialogs. A profile whose storage cannot be opened cleanly then opens degraded, without a dialog or event; the host cannot currently detect or report that. Malformed, truncated and oversized input closes the session and shuts down the host. Unknown protobuf fields are ignored. Stable majors never reuse field numbers; unstable contract changes follow AGENTS.md. Clients must continuously drain stdout, including events, and stderr, where Chromium and the host write diagnostics as they happen: a full stderr holds up the host.

Requests carry a correlation ID. Responses echo that ID. Events use a separate typed Output body. Initialization/status reports actual GPU acceleration, backend, a diagnostic fallback reason and enabled capabilities. Software renderers such as SwiftShader and llvmpipe are never reported as hardware acceleration.

## Version handshake

A binary speaks exactly one protocol major: the major of its package version in `Cargo.toml`, which is also its release storage prefix (0004-releases.md). Paths, the protobuf package, capability tokens and messages carry no other major. Version may be sent at any time, including before Initialize, and has no side effects. Its response contains `major` and the optional build number `YYYYMMDD.N` compiled into numbered main/support builds; development/PR binaries have none. A supervisor must send Version before any other request and stop without sending further commands when the major differs from the one it was built for. The engine does not check majors itself; a request it cannot decode closes the session as malformed input.

The handshake is identical in every major and never changes: the length-prefixed framing and its 65536-byte limit, `Request.id = 1` (uint64), `Request.version = 2` (Empty), `Output.response = 1`, `Response.id = 1` (uint64), `Response.error = 6` (Error with `message = 1`), `Response.version = 7`, and `Version { uint32 major = 1; optional string build = 2; }`. A new major may change any other message or field, but never these numbers, types or meanings.

## Capabilities

Initialize's field 3 accepts an Initialize message; an empty one requests no capabilities. Clients may request at most 32 capability tokens, each 1–64 ASCII lowercase letters, digits, dots, underscores or hyphens. Invalid bounds or token syntax close the session like malformed input. Unknown valid tokens are ignored and duplicates have no additional effect. Status.capabilities returns the supported tokens enabled so far for this process, in a deterministic order. Initialize adds supported requested capabilities monotonically; repeated or empty initialization never revokes them, including for existing tabs and retained callbacks. Status alone does not enable anything. Clients must check returned tokens; build/major alone does not imply optional support. Tokens are unversioned names. In a stable major, an incompatible change to a capability is a breaking change requiring a new major; new behaviour that clients must detect uses a new token name.

`loading-state` enables LoadingState events for every tab, including existing tabs and popups, on subsequent changes in Chromium's overall loading state. Each contains tab, is_loading, can_go_back and can_go_forward. Loading begins on engine-observed initiation and ends on completion, cancellation or failure. These observations are independent of command acknowledgements and main-frame Loaded events; Loaded remains URL/HTTP-status completion. Negotiation does not synthesize a current-state event. Before the first observation state is unknown. Without opt-in there are no LoadingState events. LoadingState does not provide history entries, identifiers or an exact history index, and does not promise callbacks for every same-document history mutation. Consumers may retain the last observation for live attachment snapshots; never replay it as a navigation action.

CreateTab selects a profile, URL and viewport. A profile is a persistent storage context. A named profile's name is opaque to the engine and contains 1–64 ASCII letters, digits, underscores or hyphens. An empty name creates a new unnamed profile for the tab (a request setting the `private` field, from before unnamed profiles, is refused), which only its popups share: it is stored under the data directory like a named profile, and removed with its storage once its last tab has closed, a few seconds later, since Chromium can still be finishing its writes. A host that stops before then leaves it for the next host to start on the data directory, which removes it. Shutting the host down closes no tab. Viewports are 1–8192 pixels per dimension and at most 16777216 pixels overall. The host permits at most 128 live/creating tabs. An empty URL opens `about:blank`; zero creation dimensions select 1280×800. Invalid parameters return an Error without creating a tab. Profile symlinks are refused.

Tab responses identify a tab, its profile and its local RFB socket. The profile is a named profile's name, or for an unnamed profile `~` followed by 32 lowercase hexadecimal digits, a form CreateTab and ReleaseProfile never accept. Operations cover navigation, back/forward, stop/reload, resize, control ownership and close. Navigation/title/load-completion events identify their tab; load completion includes URL and HTTP status. Event text is capped at 16384 UTF-8 bytes. Tab creation is asynchronous internally; paints and navigation may arrive after its response. Failure to create a browser within 15 seconds terminates the host so the supervisor can restart it. Tabs load only `http`, `https`, `data`, `blob` and `about:` URLs, and every `about:` URL is an empty document. CreateTab and NAVIGATE return Error for any other URL, such as `file:`, `chrome:` or `javascript:`, and DevTools `Page.navigate` refuses it. Any other navigation that reaches the browser is cancelled: the tab stays where it is and no Navigation or Loaded event follows. Pages cannot load these URLs themselves: Chromium sends a dropped one to `about:blank#blocked`, and a page's own `javascript:` links run in that page, as ever.

RFB viewers begin view-only. Connected/disconnected events supply viewer IDs scoped to their tab. CONTROL grants input to an existing viewer or revokes it with viewer zero. Only the current controller may inject keyboard/pointer input; control loss and disconnect release held input. Tab closure emits Closed and removes its display endpoint. Forced tab close and host shutdown dismiss before-unload requirements.

A popup automatically becomes a tab, reported by Popup with its opener and Tab endpoint. It inherits the opener's exact request context. Closing its opener leaves the child usable. Each unnamed profile is isolated from every other profile, named or unnamed.

JavaScript dialogs are asynchronous Dialog events. Kinds are 0 alert, 1 confirm, 2 prompt and 3 before-unload. Reply using the tab and dialog request ID, accept/dismiss and prompt text. IDs become invalid when the dialog resolves, the page resets it or the tab closes. A reply for another tab is rejected. Native browser context menus are suppressed without the opt-in below; page-rendered menus still work.

ReleaseProfile releases an idle profile's persistent request context. Close its tabs and await Closed events first; release while tabs/popups remain returns Error. It does not delete stored cookies or site data. Only named profiles are released; an unnamed profile's lifetime follows its last tab.

Only the environment supervisor receives control stdin. Semantic automation, file-byte transport and audio remain outside this engine protocol. Clipboard exchange is limited to the explicit `clipboard` transfers below.

## Restarts

Every tab is saved under the data directory, each in a file of its own replaced whole, and a later host on that directory resumes it: after a crash, after an ordinary shutdown and after an update to a newer build. Shutting the host down closes no tab; only CLOSE and a page closing itself do, and a closed tab is never restored. What comes back is each tab's ID, profile and viewport, its back/forward history with each entry's page state (form values, scroll position and `history.state`) and its place in that history. Its profile's cookies, session cookies included, and site storage were never anything but stored, though Chromium writes cookie and storage changes in batches, cookies up to about 30 seconds apart, so a crash can lose the latest. The current entry loads again; a `blob:` entry's object went with the host that made it, and a page that was the answer to a form's POST comes back only if Chromium's cache still holds it. A posted form's password is never saved, so a page that answered a form with a password doesn't come back from the cache either, and an iframe that showed a form's answer loads the last address it showed again, without the form. Each tab's `sessionStorage` comes back with it, a popup's being its own, which starts as a copy of its opener's unless the page opened it with `noopener`. A closed tab's `sessionStorage` stays on disk until its profile is next loaded, by this host or a later one, without saved tabs of that profile still to come back, and only once the tab is forgotten on disk, so a tab a crash brings back still has it; an unnamed profile's goes with the profile. A tab's snapshot is bounded: entries past about 40 MiB of a history's addresses and page state come back without their page state, and if even their addresses don't fit, only the current entry and those that fit come back. Restoring is bounded too: Chromium keeps a copy of a frame's page state for each frame it is nested in, so past about 512 MiB of that across a host's restored tabs, entries come back without their page state. A popup comes back as a tab of its own in its opener's profile, without `window.opener`. Nothing that lives only in a running page or in this process comes back: the page's script state, connections and timers, its viewers and CONTROL, DevTools sessions, recordings, dialogs, IME compositions, clipboard transfers and unfinished downloads.

The first Initialize restores the saved tabs and answers once they are back, so ListTabs then lists them. A restored tab keeps its ID, emits its usual Navigation and Loaded events and has a new RFB socket. Tab IDs are never handed out twice on a data directory, across every host that uses it, so an ID a supervisor kept names the same tab or none. Tabs created before the first Initialize get new IDs and stay as they are. A saved tab that doesn't fit within the 128-tab bound, whose profile is being released, or whose display can't be set up stays saved, with its profile, for the next host, and Initialize answers without it. `discard_saved_tabs` makes the first Initialize remove the saved tabs and their unnamed profiles instead; a supervisor uses it to stop restoring tabs that keep crashing the host. A restored tab is created within the same 15 seconds as any, or the host ends, and the next reports CRASHED.

Status.previous_exit says how the previous host on the data directory ended: FIRST_RUN when none has run, or only builds from before restarts, whose tab IDs were never recorded and may be handed out again, CLEAN when it shut down and saved every tab, or CRASHED when it ended any other way. One host uses a data directory at a time: another started on it before the first has exited stops with an error, so an update starts the new host once the old one has gone. A tab whose ID the host can't record on disk is refused, or for a popup closed, with no event naming it, rather than risk its ID being handed out again. The record of IDs handed out is in the data directory from the first run on; a host that finds it missing or unreadable after that stops with an error rather than reuse them. Saved state lags a tab by about a second, and a page's renderer reports changes such as typing about a second after they happen, so even a clean shutdown can miss the last moments, and a crash more: a tab created just before a crash can be missing, and one closed just before it can come back.

ListTabs lists each tab's ID in `tabs` and its whole Tab in `details`, in ID order.

## Not implemented yet

`file-dialog`, `downloads` and `user-preferences` are not implemented: the host doesn't grant their tokens, file dialogs and downloads are cancelled, and the launch flags for preferences have no effect. The sections below describing them are the contract they will meet, and it may change where Chromium allows something better. The cleanup DevToolsClosed describes is not implemented either: when a session ends, the host detaches its client and relies on Chromium's own teardown of that client's session, reporting DevToolsClosed once Chromium has detached it, without sending the resets listed there or waiting for them. Until `user-preferences` is implemented, DevTools media and user-agent overrides reach Chromium as a session sends them, `acceptLanguage` included: what the DevTools section says of the host colour scheme, languages and preferences applies once it is.

## Optional file and native-menu callbacks

`file-dialog`, `downloads`, and `native-context-menu` independently enable the corresponding callbacks, including for existing tabs and popups. Without opt-in file dialogs and downloads are canceled deterministically and native context menus remain suppressed; no server desktop dialog is opened. `file-dialog` implements open-single and open-multiple only. Folder and save dialogs cancel; this token does not advertise folder upload. Downloads have their own approval protocol.

FileDialog carries tab, one-shot request ID, captured controller viewer (zero means supervisor), multiple-selection flag, title and accept filters, each with the extensions it stands for and a description. FileDialogReply accepts 1–32 readable regular server files, exactly one for single selection, or cancels with an empty list. Files must use absolute canonical UTF-8 server paths of at most 4096 bytes, without symlink components. These paths are never client-local paths. The supervisor authorizes/stages uploads before replying; Chromium then reads those files into the page's file input. Engine selection does not delete supervisor-owned uploads; the supervisor must remove staged artifacts after their use, cancellation or failure and when the tab's unnamed profile ends.

DownloadRequested carries tab, request ID, host-scoped download ID, captured viewer, suggested basename and MIME type. Suggestions are labels, never trusted destinations. DownloadReply cancels with an empty path or supplies a server-local absolute UTF-8 destination (maximum 4096 bytes) in an existing canonical real directory. The destination must not already exist. Chromium writes into an exclusively created mode-0700 staging directory under that parent. After Chromium completes it, the engine publishes the mode-0600 file using an atomic no-overwrite hard link, then removes its staging directory (including any Chromium temporary files). A destination created concurrently is preserved and publication fails. The supervisor must authorize a private trusted parent directory whose contents cannot be replaced by untrusted processes. No byte transfer happens on this wire. On success the supervisor owns the completed file and its local-client transfer and cleanup, including cleanup when its unnamed profile ends. Unfinished/canceled/interrupted destinations remain engine-owned and are removed once Chromium ends the download or the host shuts down. Accepted downloads survive ordinary navigation; pending approval is canceled on main-frame load start. Tab close/renderer termination cancels its downloads. CancelDownload applies to a live download of that tab. DownloadUpdated reports signed received/total bytes (the total may be unknown), state and Chromium's interrupt reason. A failed staging-directory removal sets cleanup_failed; its deterministic name is `.lanescape-browser-download-PID-DOWNLOAD` under the authorized parent, where PID is the engine process ID and DOWNLOAD the host download ID. The supervisor must recover cleanup of that engine-owned directory. A failed final publication reports INTERRUPTED with publish_failed; it never overwrites an existing destination. Progress is coalesced to at most one event per 100 ms per download; terminal updates are immediate and emitted once. Once a tab has closed, Chromium may stop sending updates for its downloads; the engine cancels each one, irrevocably retires publication authority, removes its staging directory and emits its own terminal CANCELED update with the latest observed byte counts. Updates may precede approval. A command acknowledgement does not imply completion or cancellation; await the terminal update. Complete means Chromium finished the server file, not that a viewer received it.

ContextMenu lists what a person could do at that point, in viewport coordinates: Chromium offers an embedder no menu of its own, so the host builds it from what Blink says the page can do. Back, Forward, Undo, Redo, Delete and Select All come with their fixed command IDs when they apply. Items carry kind (1 command, 4 separator), label and enabled state. ContextMenuReply selects an enabled command in that list or cancels. Without `clipboard`, Cut, Copy, Paste and Paste and Match Style are disabled and can't be selected. With `clipboard` they keep their enabled state; see Native IME and clipboard for how they complete. Touch quick menus are not part of this capability.

InteractionClosed identifies the resolved/invalidated request and kind (file dialog, download approval or context menu). Request IDs are host-scoped, never reused within the process, bound to a tab, and one-shot. Wrong-tab/expired/duplicate requests and unavailable menu commands return Error without executing. Invalid selections/destinations return Error and leave approval pending for retry/cancel. Pending requests invalidate on relevant main-frame navigation, tab closure, renderer termination and EOF/shutdown. Menus also invalidate when Chromium dismisses them. Pending requests capture the initiating RFB controller. CONTROL with viewer zero releases browser input for a client modal picker without canceling its request. A replacement nonzero controller or captured viewer disconnect retires the pending authority. The supervisor must also dismiss UI and cancel staged work when InteractionClosed arrives. The trusted supervisor remains responsible for authentication and authorizing replies; viewer IDs are attribution, not bearer credentials.

The engine retains at most 64 file callbacks, 64 menu callbacks and 64 live downloads across the process. Each snapshot string is at most 4096 UTF-8 bytes; file filters are at most 64 entries. Menus allow at most 256 items including hidden entries and nesting through depth eight (root depth zero). The entire Output envelope must fit 65536 bytes; oversized file/menu snapshots cancel safely as a whole, without truncating meaning or exposing a partial interaction. All retained callbacks are resolved/released on the UI thread. No optional callback requires a display server, GPU, or weakened sandbox.

## User preferences

Colour scheme, timezone and languages form one host-wide group, UserPreferences, that applies to every profile and tab. The host often runs on a different machine from the user, so its own settings mean nothing to the user and there is no "system" value. An unset value means its launch value, or Chromium's default when the launch flags left it unset.

The supervisor sets the group at launch with `--color-scheme=light|dark`, `--timezone=ID` and `--languages=TAG,TAG`, because Chromium starts processes that must inherit them, such as Linux's zygote, before the host reads its first control message. The last occurrence of each flag wins and an empty value is unset; an invalid value stops the host with an error. `user-preferences` enables SetUserPreferences and tells the supervisor that the flags were understood: the host passes switches it doesn't know on to Chromium, which ignores them, so check Status.capabilities before relying on them. SetUserPreferences replaces the whole group and returns Ok, or Error with nothing changed. A timezone is 1–64 ASCII letters, digits, `/`, `_`, `+` and `-` in non-empty `/`-separated parts; the supervisor checks names against its own tz database. Languages are at most 16 distinct well-formed BCP 47 tags of at most 35 bytes, in preference order. They set Accept-Language and `navigator.languages`, and the first sets the default `Intl` locale, so it must not be a private-use tag.

At launch the timezone becomes `TZ` in the host's environment, the colour scheme a `--blink-settings` preferredColorScheme entry, and the languages every browser context's Accept-Language list, so first documents, workers, unnamed profiles and popups get them. Every request context starts with the launch languages. The engine also sends every tab, on its own DevTools channel and with or without a client session, prefers-color-scheme media emulation, a user-agent override carrying the languages, a locale override and a timezone override; the `Intl` locale has no other route. A tab created while any preference is set first loads an unreported about:blank, so its renderer applies these overrides before the requested URL loads. That about:blank emits no events and leaves no history entry, and CreateTab waits up to 5 seconds for it. SetUserPreferences re-sends the overrides to every tab. Every tab gets the same values, so no renderer process sees two different overrides. A renderer process holds one timezone and one locale override, owned by the first tab there to set it and cleared when that tab leaves the process. When a tab closes or navigates, the other tabs in the renderer process it was in re-send theirs for 2 seconds to take the overrides over; until then they can briefly see the launch timezone and Chromium's default locale.

Accepted gaps: anything outside an overridden tab's renderer process misses the overrides, such as out-of-process iframes and service workers running elsewhere. These keep the launch values, and the `Intl` locale has no launch value. After a change, dedicated workers keep the launch languages, and processes without an overridden tab keep the launch timezone and colour scheme until the host restarts. A popup gets the overrides once its renderer answers them, which may be after its first document's scripts run. A tab's first document can see its unreported about:blank in `history.length` until its commit completes.

## DevTools sessions

`devtools` enables OpenDevTools. OpenDevTools names a tab and returns DevTools with that tab, a session ID and a socket path. It returns Error without negotiation, for an unknown tab, when the tab already has a live session (each tab has at most one), or before the tab's previous session has reported DevToolsClosed. Session IDs are scoped to the host process, never reused and bound to one tab. Popups are separate tabs with their own sessions.

The socket is an owner-only (mode 0600) Unix socket in the engine's runtime directory. It accepts exactly one connection within 15 seconds and its path is removed once connected. Each message is one UTF-8 JSON object followed by a NUL byte, at most 64 MiB, carrying standard Chrome DevTools Protocol. A client command contains only `id` (0 to 2147418111; higher IDs are reserved for the engine), `method`, an optional `params` object and an optional `sessionId` naming a child session attached through flattened `Target.setAutoAttach`. Any other shape, an `id` already in flight, or an oversized message is a protocol violation. At most 256 commands are in flight; beyond that the engine stops reading until responses return. The engine forwards each command under its own never-reused ID and restores the client's ID in the response, so a reply owed to an earlier client never reaches a later one. Ordering between CDP messages and control-channel events is not promised, except that a DisplayFence covers work a client awaited before sending it (Display fence).

A session reaches what the tab's pages and a person at them can reach, frame by frame, and nothing Chromium hides from page script. Runtime, DOM, DOMSnapshot, CSS, Accessibility, Overlay, Log, Debugger, Performance, Animation, Inspector, Audits and Fetch are available. Page, Input, Emulation and Network offer only reviewed methods: reads, page traffic, navigation, input and overrides the engine resets. Their unreviewed methods, including ones Chromium adds later, are refused, as is every other domain, including DOMDebugger. Notable refusals and restrictions:

- Page: `navigate` to a URL a tab may not load (Chromium acts on debug URLs such as `chrome://kill` before any navigation starts), `startScreencast`, `stopScreencast`, `screencastFrameAck`, `startScreenRecording`, `stopScreenRecording` (RFB is the display), `setInterceptFileChooserDialog` (FileDialog), `handleJavaScriptDialog` (Dialog), `setDownloadBehavior` (DownloadRequested), `close`, `crash`, `printToPDF`, the deprecated emulation aliases (`setDeviceMetricsOverride`, `setTouchEmulationEnabled`, geolocation and device-orientation overrides), `setWebLifecycleState` (a frozen page cannot be made visible again), the deprecated `addScriptToEvaluateOnLoad` pair, `addScriptToEvaluateOnNewDocument` naming a world (Chromium gives named worlds universal access), and overrides the engine cannot undo (`setFontFamilies`, `setFontSizes`, `setPrerenderingAllowed`, `setSPCTransactionMode`, `setRPHRegistrationMode`). `createIsolatedWorld` is forwarded with `grantUniveralAccess` false: a world never reaches beyond its page's origin.
- DOM: `getFileInfo`, which reveals server paths hidden from the page, and `setFileInputFiles`, whose paths name files nobody authorized. A session reaches a file input by clicking it, which raises FileDialog for the supervisor to answer.
- Input: every command while a nonzero viewer controls the tab, checked again immediately before dispatch, and `setIgnoreInputEvents` always. `dispatchKeyEvent` requires `modifiers` of 0–15 and key codes of 0–65535; with clipboard editing `commands` or a clipboard shortcut (Ctrl or Meta with C, V, X or Insert; Shift with Insert or Delete; the Copy, Cut and Paste keys) is refused because the browser clipboard is shared beyond the tab. Synthetic gestures are refused because Chromium continues them after the session ends. `dispatchDragEvent` carrying files is refused like `DOM.setFileInputFiles`.
- Emulation: `setTimezoneOverride` and `setLocaleOverride`, because the timezone and locale are host-wide user preferences and each override applies to a whole renderer process. Otherwise only `canEmulate` and overrides the engine resets are available: focus, media, touch, mouse-as-touch, user agent, geolocation, script execution, CPU throttling, default background, auto dark mode, vision deficiency, scrollbars, idle state and `document.cookie` disabling. Media emulation keeps the host colour scheme unless the session emulates `prefers-color-scheme` itself. `acceptLanguage` in either user-agent override (Emulation or Network) is replaced with the current languages, or removed when they are unset. A change of user preferences keeps a session's own media and user-agent overrides; one that Chromium rejects is dropped, and the host values apply alone. Viewport size belongs to RESIZE.
- Network: cookie-jar reads and writes (`getCookies`, `getAllCookies`, `setCookie`, `setCookies`, `deleteCookies`, `clearBrowserCookies`, `setCookieControls`), `clearBrowserCache`, `loadNetworkResource`, the deprecated interception methods, and overrides and profile state the engine cannot undo, such as `setAcceptedEncodings`, `overrideNetworkState` and device-bound sessions.
- Target: everything except `setAutoAttach`, `getTargetInfo` without a target ID (the tab itself) or for its attached children and `detachFromTarget` for its own children.
- Browser: everything except `getVersion`.

A session can navigate its tab to any web origin, so origin is not a boundary within the tab's profile; response bodies the page received are readable. The boundaries are the profile, named or unnamed, the browser and host, including the host's files, and data no page script can read, such as HttpOnly cookie values. Refusals are CDP error responses with code -32000 and a message starting `Lanescape browser: <method>`. Cookie, Set-Cookie, Authorization and Proxy-Authorization headers, raw header text, raw cookie lines and cookie lists are removed from Network, Fetch and Audits messages; cookies that aren't HttpOnly remain readable through page script, and credentialed requests still carry every cookie. Dialogs, file pickers, downloads, native context menus, viewport size and display stay on the control channel and RFB.

DevToolsClosed reports each session's end exactly once with a reason: CLIENT (disconnect or socket error), REQUESTED (CloseDevTools), TAB_CLOSED (emitted before the tab's Closed), OVERFLOW (more than 128 MiB queued for a client that isn't reading, or an event over 64 MiB; a response over 64 MiB fails only its command), PROTOCOL, CONNECT_TIMEOUT or SHUTDOWN. Each client attaches its own session to the tab, and Chromium undoes what it set when it detaches. When a session ends for any reason except TAB_CLOSED or SHUTDOWN, the engine stops forwarding its queued commands, detaches its child sessions, removes the scripts and bindings it added, and resets auto-attach, request and drag interception, the debugger, every allowed emulation override, network conditions, blocked URLs, extra headers, CSP bypass, ad blocking and the inspect overlay, then disables event domains and re-applies the user preferences. The engine waits up to 5 seconds for the tab to apply this cleanup, and for replies to script registrations sent to the tab so it can remove those scripts too; commands never sent are discarded without waiting. DevToolsClosed is emitted once cleanup is complete, so a navigation after it carries none of the client's state, and OpenDevTools for the tab succeeds from then on. Tab closure and shutdown end any wait at once, still emitting DevToolsClosed before Closed. Engine diagnostics never record CDP payloads.

## Display fence

`display-fence` enables DisplayFence, which orders a tab's frames against its page. DisplayFenced names the tab and a framebuffer sequence S (0003-display.md). Frame S and every later frame of the tab include every DOM, style and layout change and every animation-frame callback in the main frame's renderer process that finished before the engine read the request, including work a client awaited over DevTools before sending it. The response is sent once frame S is published, so one full update request always reaches it. The fence produces a frame whether or not the page changed. A fence before the tab's first paint waits for that paint.

Clients must see the token in Status.capabilities first: a build without the capability cannot decode the request, which closes the session as malformed input. A build that has it but has not enabled it returns Error.

While a JavaScript Dialog of a frame in the main frame's renderer process is pending, its main thread is blocked and cannot draw, so the fence answers at once with the latest frame: what a person at the page sees. A dialog from a frame in another process does not block, and the fence proceeds as usual. A change the page made just before the dialog can be missing from that frame. The Dialog event precedes such an answer on this channel, so a client can tell, and the first fence after the dialog closes includes the change.

Errors use the Error response: an unknown or closed tab, a tab that closes or a renderer that terminates while its fence is pending, a fence on a tab whose renderer has terminated until a navigation replaces it, host shutdown, and more than 64 fences outstanding across the host. A fence not answered within 5 seconds, as on a renderer too busy to draw, fails. Chromium cannot cancel a redraw, so a tab runs one at a time: fences read during it share the next, and one that fails is tried again until the fence's 5 seconds end. A main-frame navigation replaces a tab's running redraw, and fences waiting for it take the new document's.

Accepted gaps: a change in an out-of-process iframe appears when that iframe's renderer draws it, so the fence does not order it. A client that waits for two animation frames in the iframe's DevTools session before sending the fence narrows this: in tests it gets past a renderer that was busy, but not one slow to rasterize. An offscreen or `display:none` iframe never fires them and shows nothing, so bound that wait. The fence promises nothing about RFB input, which arrives on another channel. A fence is answered by the first capture that began after its redraw finished.

## Recording

`recording` enables StartRecording and StopRecording, which stream what a tab shows as VP8, at the tab's size and at most 30 frames a second, without viewers. A tab has at most one recording and the host at most 32 (Error beginning `LIMIT`). StartRecording returns Recording with the tab, a recording ID scoped to the host process and a socket path. A tab that hasn't painted yet starts recording at its first paint. It returns Error without negotiation, for an unknown tab, and when the tab is already recording, until its RecordingEnded.

The socket is an owner-only (mode 0600) Unix socket in the engine's runtime directory. It accepts one connection within 15 seconds and its path is removed once connected. The reader receives an IVF stream, which ffmpeg and others read directly: a 32-byte header with the `VP80` format, the first frame's size, a timebase of milliseconds and a frame count of zero, since a stream's isn't known, then each frame as a 4-byte little-endian size, an 8-byte little-endian timestamp and its data. It starts on a key frame, timestamps only go forward, and a page with nothing changing sends nothing, so frames are not evenly spaced. After a resize it continues with a key frame of the new size, which the header doesn't reflect.

A reader that falls behind costs nothing but its own frames. At most 8 MiB waits for it; beyond that what's queued is dropped and the stream resumes at a forced key frame, so what it receives still decodes. A slow reader holds up neither the page nor another recording. An encoder that can't keep up loses captures the same way.

StopRecording returns Error if the tab isn't recording. It flushes the encoder, and the reader receives the last frames and the end of the stream. RecordingEnded follows, with the tab, the recording, the frames its reader received whole, the frames it lost for falling behind and a reason: STOPPED, TAB_CLOSED, CONNECT_TIMEOUT, READER_CLOSED or SHUTDOWN. A reader has 5 seconds after that to take what's left, or the stream ends without it. Encoding runs on the CPU in both rendering modes.

## Native IME and clipboard

`native-ime` and `clipboard` let the viewer that holds CONTROL of a tab compose text with its own platform input method and move clipboard contents between its own clipboard and the page. Keys, pointer and wheel stay RFB messages; RFB `ClientCutText` stays bounded and discarded. The rule matches DevTools page parity: the controlling viewer can do what a person at the page could do with their own keyboard and clipboard, and the page learns nothing more. The host advertises each token only when its engine supports it; check Status.capabilities. Without the token, its requests return Error and its events are never emitted.

Every ImeInput, ClipboardTransfer, ReadClipboardTransfer and ClipboardOperation names a tab and a viewer and is accepted only while that viewer holds CONTROL of that tab, checked on receipt and again immediately before it reaches the page. A request for another tab, from a viewer without CONTROL, or made while a JavaScript Dialog of the tab is pending returns Error without queuing. Event `viewer` fields name the controller the event belongs to.

Ordering. Keys travel on RFB and these requests on the control channel, so ImeInput and ClipboardOperation carry `after_rfb_input`: the number of RFB KeyEvent and PointerEvent messages the client had sent on that viewer's connection before the request, counting every such message from the start of the connection, including pointer motion and messages sent while the viewer had no CONTROL. The engine counts the messages it has received and processed per connection and holds the request until that count is reached. A held request is refused with Error when the connection closes, CONTROL changes or the tab closes. The host holds at most 64 requests; beyond that a request returns Error. Reaching the page is ordered too, though input and these requests take separate paths there: a request waits until the page has answered the key and button events sent before it, for at most 2 seconds, and input that follows waits for it to start. So typing, IME text and pastes land in the page in the order they were sent, however busy the page is. While an ImeInput is being applied, the host holds the tab's further RFB input. Held RFB input is bounded: at most 256 messages per connection and 1024 across the host. A connection that would exceed either is closed, like any misbehaving viewer, with the usual disconnect. A request's response is sent once it has been applied or refused, not while it is held. The counter says which RFB input comes first; input received after that follows the request.

### IME

Each renderer reports focus changes in its frames, including out-of-process iframes. The engine mints an editor ID, scoped to the host process and never reused, for each report of an element that takes text, and when CONTROL passes to a nonzero viewer while one is focused, so each controller receives its own editor ID in an EditorState. What takes text is what Chromium tells a local input method (Blink's text input type): text fields that are neither readonly nor disabled, content-editable elements, and a document in `designMode` once it has a caret. Other controls don't, and `role=textbox` alone makes nothing editable. Deciding runs no page script. A change without a focus change, such as a click in a `designMode` document or a field made readonly, is noticed within about 200 ms and reported. Only the frame the browser has focused can say where focus is: a report from any other frame changes nothing. An accepted report of no editable element retires the editor, as do another frame taking focus, CONTROL moving to another viewer or to zero, main-frame navigation, navigation or detachment of the editor's frame, renderer termination, tab close and EOF.

EditorState carries tab, viewer, editor (zero: no focused editor), composing, the caret rectangle, the composition's character bounds and `inline_composition`, in the tab's viewport pixels, whichever frame the editor is in. It is emitted when any of them changes; consecutive states may be coalesced, but the latest is always delivered. `inline_composition` is true for every editor: the page shows the composition itself, as with a local input method, in out-of-process iframes as anywhere else. While composing, character bounds hold one rectangle for each UTF-16 code unit of the composition, at most the first 1024, and the caret is the one Blink draws, in any text direction. Each comes from the renderer with its request's result, and they follow the page: its layout, its scrolling and a parent moving its iframe are noticed within about 100 ms. A new composition's state is complete when its response is sent. Outside a composition, the caret is the editor element's bounds when its focus was reported; scrolling, zoom and resize do not update them.

ImeInput names the current editor; a request for any other editor returns Error `not the current editor`. PREEDIT sets the composition text (at most 16384 UTF-8 bytes), its selection and at most 64 underlines. Offsets are UTF-16 code units within that text, with exclusive ends: `selection_start` ≤ `selection_end` ≤ length, and each underline has `start` < `end` ≤ length. The selection is applied as given, a range as well as a caret. Colours are 32-bit ARGB; zero means the engine's default. Underline and background colours are rendering hints the engine may not honour. Out-of-range values return Error. The page receives `compositionstart`/`compositionupdate` as with a local input method and draws the underlines; COMMIT inserts its text and ends the composition, FINISH ends it keeping the composition text, and CANCEL removes it. CANCEL, or an empty PREEDIT, with nothing composing changes nothing, and in particular leaves a selection alone. Keys the input method consumes are not also sent over RFB. When focus leaves an editor while composing, or a navigation the page starts itself replaces its document, the editor is retired and the page keeps the composition text, as with a local input method. NAVIGATE, BACK, FORWARD and RELOAD cancel any composition before they navigate, and CONTROL moving to another viewer or to zero, renderer termination, tab close and EOF cancel it too. Each of these emits EditorState with composing false.

Once a request is due, the editor's frame must still be the browser's focused frame. The frame's renderer then applies it as one step with a last check that its report is still the latest and that its element still has focus, in a focused frame, and still takes text, so nothing can come between the check and the action. Otherwise, or if the frame goes away, the request returns `not the current editor`. A renderer has 2 seconds from when the host sends a request to start it, and later refuses it; the host answers for a request after 5 seconds with the same Error and takes it back if it hasn't gone. A page's own `compositionstart` handler can take longer than that: the request is then refused, yet the composition that handler's return completes is still followed in EditorState and still cleaned up. A cancel the engine sends itself, as when CONTROL moves, never expires. Clients should send ImeInput only for the editor ID of the latest EditorState.

### Clipboard

Every clipboard exchange is explicit, one-shot and owned by the controlling viewer, and never touches the host operating system's clipboard: a copy gets what the page offers in that frame, and a paste offers the page the text it was given. With `clipboard` enabled, Status.clipboard_formats lists the MIME types the engine accepts in both directions, in preference order; currently exactly `text/plain`. Clients offer and request only listed formats. Each transfer holds one representation of one clipboard item in one format; an operation may carry several representations of the same item, at most one per format.

Clipboard data moves through transfer buffers, since it can exceed one frame. ClipboardTransfer CREATE names a listed format and the exact size and returns ClipboardRepresentation with a new transfer ID. WRITE appends at most 49152 bytes at an offset equal to the bytes already written. SEAL requires exactly the declared size and valid data for the format (valid UTF-8 for text types). RELEASE frees a transfer. ReadClipboardTransfer returns ClipboardChunk with at most `length` bytes (zero or above 49152 means 49152) from an offset within a copied representation, with `end` set on the last byte; an offset at or past its end returns Error. Transfer IDs are scoped to the host process, never reused and bound to one tab, one viewer, one direction and one format. A representation is at most 1 MiB for text formats; each further format gets its own limit when it is listed. An operation carries at most 8 representations; a tab holds at most 16 live transfers and the host at most 64. CREATE with an unlisted format, an oversize CREATE, an out-of-order or overflowing WRITE, a failed SEAL and an allocation beyond a limit return Error with nothing changed; the messages begin `UNSUPPORTED_FORMAT`, `TOO_LARGE`, `INVALID_DATA` or `LIMIT`.

ClipboardOperation's request ID is its operation ID; zero and an ID already pending return Error, because operation zero identifies copies chosen from a context menu, which always carry their nonzero `menu_request`. ClipboardCopied and ClipboardFinished never carry both operation and menu_request zero; that combination is reserved. Its response acknowledges admission; each admitted operation ends with exactly one ClipboardFinished carrying its status. Every browsing context, whether a named or an unnamed profile, has its own clipboard, so one host serves any number of them: a context's data is offered only to the frame running its current operation, and only while it runs. Within a context, operations run one at a time in admission order, and tabs share that queue, as one person's tabs do. A slow page holds up its own context alone. Popups take their opener's. At most 64 operations wait or run across the host; beyond that ClipboardOperation returns Error beginning `LIMIT`, as does a COPY or CUT that accepts a listed format when its tab or the host has no room left for the read transfer it may produce. CONTROL, pending dialogs and focus or document changes since admission are checked again immediately before the page's command is sent.

The page's command runs only if its renderer starts it within 500 ms of its sending; a command its busy renderer reached later is refused unrun and sent again with a new 500 ms limit, while the operation still holds and less than 5 seconds have passed since it was first sent. When the frame holds the focused editable element, it runs only while that is still the focus the engine last saw reported. Otherwise it never runs and the operation finishes CANCELLED. It carries the user activation a person's own key press would, and the page sees no key it wasn't sent. Once started, the command holds its context's clipboard until it ends, however long the page's own event handlers take, or until its frame or renderer goes away or its tab closes: later operations in that context wait in the queue. An operation cancelled before its command has reached the page never runs. One cancelled later, for example by a CONTROL change, reports CANCELLED at once, but the command may still run; its result is then discarded, and the operation keeps the clipboard until its renderer reports that the command ran or was refused.

- COPY and CUT list in `accept` the formats the client can take. The engine runs the focused frame's Copy or Cut, out-of-process iframes included; the page receives its normal trusted `copy` or `cut` event and may change or cancel the data. Representations in both `accept` and Status.clipboard_formats become new read transfers, listed by ClipboardCopied; ClipboardFinished then reports DONE. Other formats the command produced, such as `text/html`, are discarded. Without a representation it reports NOTHING_SELECTED when the frame's document had no selection, DENIED when it had one and yet nothing was copied (the page cancelled the event, or the field refused copying), UNSUPPORTED_FORMAT when `accept` lists no listed format (the page's command then does not run) or the command produced only unlisted formats, and TOO_LARGE above the format's limit. Copied and pasted text is delivered exactly. The client writes all representations to its own clipboard as one item and releases the transfers. What a page writes reaches the host a moment after the command finishes, on a path of its own, so a command that wrote nothing is known only after waiting up to 500 ms, and its answer takes that long.
- PASTE and PASTE_PLAIN carry sealed write transfers. For that one operation the engine offers exactly those representations to the focused frame, and runs its Paste (PASTE_PLAIN: Paste and Match Style, offering only text); the page receives its normal trusted `paste` event and chooses what to insert. The frame's renderer checks, as the command runs, that the focused element takes text (as defined under IME); otherwise the page receives nothing and ClipboardFinished reports NOT_EDITABLE. DONE means the page received the event, whether or not it cancelled it. The transfers are consumed on admission whatever the outcome, and naming one again returns Error. ClipboardFinished reports DONE, NOT_EDITABLE or CANCELLED.

Anything else a page writes, outside an operation, goes nowhere: a page's own "copy to clipboard" button or script, or a copy or cut key sent over RFB. Selecting text puts it nowhere either.

A page reads nothing outside a paste operation. In every profile, named or unnamed, `navigator.clipboard.read` and `readText` are refused at once with a permission denial, without a prompt or a stored per-site decision, and `execCommand('paste')` does nothing. `navigator.clipboard.writeText` with a user gesture succeeds, and its text is discarded. RFB Ctrl+V, Ctrl+Shift+V and Command+V are dropped, since no viewer's clipboard is behind them, and Insert is not mapped. The context menu's Paste items are disabled without `clipboard` and complete only through ClipboardOperation with it. A middle click finds an empty selection buffer. Copy and cut keys sent over RFB (Ctrl or Command with C or X) are not clipboard operations: they reach the page as ordinary key events, so a page that handles them itself, such as a web terminal using Ctrl+C, keeps working, and whatever they write goes nowhere. On Linux an RFB cut therefore removes the selected text without delivering it anywhere. Clients that want a person's copy, cut and paste shortcuts to move data between the viewer and the page send them as ClipboardOperation instead of RFB keys. Everything in Chromium that would reach the operating system's clipboard goes to an inert one that keeps nothing, including the clipboard a service worker gets.

With `clipboard` and `native-context-menu` negotiated, the clipboard items have fixed command IDs: Cut 112, Copy 113, Paste 114 and Paste and Match Style 115. Choosing Cut or Copy by ContextMenuReply resolves the menu and runs the same flow on the focused frame for its captured viewer, reporting ClipboardCopied and ClipboardFinished with that `menu_request` and an operation ID of zero. Paste and Paste and Match Style cannot complete without the viewer's data and cannot be chosen by ContextMenuReply, which returns Error: the client answers them with ClipboardOperation PASTE (requires an enabled 114 in that snapshot) or PASTE_PLAIN (requires an enabled 115), carrying `menu_request`, which also resolves the menu. A menu dismissed or invalidated before that operation is admitted refuses it.

CONTROL moving to another viewer or to zero, a focus or document change, tab close and EOF finish every pending operation CANCELLED and free its transfers; after a focus or document change, an operation whose page command already ran completes as usual. The same events free every write transfer, so an upload never reaches a field or document other than the one it was made for; an upload named after such a change returns Error, as a freed transfer does, even when the engine has not yet freed it. Read transfers carry copied data out of the page, not into it: they survive focus and document changes and are freed on RELEASE, CONTROL change, viewer disconnect, tab close and EOF. When the engine cannot tell which transfers an operation holds, it retires the viewer's whole clipboard scope rather than guessing. Transfers live only in memory and die with their tab.

DevTools sessions are unchanged: `Input` stays refused while a viewer controls the tab, clipboard shortcuts and editing commands stay refused, and a session observes only the page's own `composition*`, `copy`, `cut` and `paste` events. Engine diagnostics may record tab, operation and transfer IDs, sizes and statuses, never clipboard or composition text or caret positions.
